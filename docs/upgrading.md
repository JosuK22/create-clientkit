# Upgrading and re-running

Two ways to run ClientKit against a project it already generated, with
different guarantees. Use `upgrade`.

## `upgrade`

```sh
npm create clientkit@latest upgrade ./acme-site
npm create clientkit@latest upgrade ./acme-site -- --styling bootstrap
npm create clientkit@latest upgrade ./acme-site -- --styling bootstrap --dry-run
```

`upgrade` reads the stack the project recorded in `.client-site.json` and
re-generates the files the current ClientKit would generate for it. Any flag
you pass overrides one recorded value, so `--styling bootstrap` means
"everything as before, but Bootstrap" — no need to repeat the site name, URL or
the rest of the stack.

Before writing, it lists every file it would **replace**, every file it would
**add**, and every file the new stack **no longer generates**, then asks.

What it guarantees:

- **Nothing is deleted.** Files the new stack no longer generates are listed and
  left where they are, for you to remove after looking at them.
- **Files ClientKit did not plan are never touched**, including your own.
- **You must confirm.** `--yes` is refused rather than treated as consent, and
  so is a run without a terminal. `--dry-run` needs neither, because it writes
  nothing.
- **A failure changes nothing.** If any write fails, every file already replaced
  is restored.

### Read this before you confirm

- **Replaced files lose your edits.** A generated file you have changed is
  replaced with the generated version. Commit first so you can review the diff
  and bring your changes back.
- **The site description is reset.** It is not recorded in `.client-site.json`,
  so an upgrade writes ClientKit's default. The command warns you and shows the
  wording it would write. To keep yours, pass it in a config file:

  ```json
  { "site": { "description": "Hand-built orreries for discerning collectors." } }
  ```

  ```sh
  npm create clientkit@latest upgrade ./acme-site -- --from description.json
  ```

- **It compares against today's templates only.** It does not know what an
  older ClientKit generated, so a file whose template changed between releases
  is reported as unchanged.
- **It does not install.** After a stack change, `package.json` is rewritten;
  run your package manager's install yourself.

### When it refuses

`upgrade` stops, without guessing, when the project:

- has no `.client-site.json`, or it is malformed
- was generated by a newer ClientKit than the one running
- records no stack (projects generated before 1.1.0)
- records a template that contradicts its recorded stack

For a project with no `.client-site.json`, `detect` reports what it is built
with and `doctor` says whether ClientKit supports it. Both only read the project.
See [docs/cli.md](./cli.md#detect).

## Re-running `create` over an existing project

This is a merge, not an upgrade:

- Without a terminal, or with `--yes`, a non-empty target directory is
  **refused** and nothing is written.
- Interactively, it lists the files it would replace and asks, defaulting to
  **no**. Confirm and your edits to those files are replaced with the generated
  versions.
- Files ClientKit did not generate are never touched, and nothing is deleted.

Re-running with a different stack adds and overwrites files, but does not tell
you which old files are now unused. For example, dropping `--ui-library mui`
leaves `src/components/ui/AppProviders.tsx` in place, still importing a package
the new `package.json` no longer lists — `npm run typecheck` will fail until you
delete it. `upgrade` reports those files for you; this is why it is the better
choice.
