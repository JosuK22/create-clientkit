# Idempotent generation

What ClientKit does when it runs again against a project it already generated,
through `create` or `upgrade`.

**The promise:** the same request against a project that already matches it
writes nothing and succeeds. A request that needs changes writes only what
differs. It never overwrites a file that may hold your work without asking, and
it never touches a file it did not plan.

```text
CLI input ─► resolve ─► template ─► validate ─► Generation Plan
                                                     │
          target directory ─► inspectTarget()        │
                                   │                 ▼
                                   └──► decideRegeneration()   the plan vs the files
                                                     │
                                         missing / unchanged / differs
                                                     │
                                   ask, only if something differs
                                                     │
                                   narrowPlan() ─► apply()    only what was decided
```

## Which directories take part

`inspectTarget()` (`src/commands/regenerate.ts`) sorts the target into:

| State          | Meaning                                                                                       | Behaviour                      |
| -------------- | --------------------------------------------------------------------------------------------- | ------------------------------ |
| `new`          | the directory does not exist                                                                  | generate                       |
| `empty`        | nothing in it, `.git` aside                                                                   | generate                       |
| `clientkit`    | its `.client-site.json` is a usable record                                                    | regenerate idempotently        |
| `unrecognised` | content, and no record, or one that is malformed, from a newer ClientKit, or records no stack | the non-empty rules, unchanged |

The record is read with the provenance reader `upgrade` has always used. It
isn't a second identification system, and project detection (`detect`) still
never reads it. A record is trusted only when the reader accepts it. Any other
record, including one written by a newer ClientKit, makes the directory
`unrecognised`, and the error's hint says why.

There is no second state file and no new metadata. `.client-site.json` is
exactly what it was.

## The decision

The Generation Plan is the expected state. `comparePlan()`
(`src/generate/compare.ts`) compares each planned file, byte for byte, with
what is on disk. It reads only the files the plan names:

| On disk                     | Called    | A re-run                                          |
| --------------------------- | --------- | ------------------------------------------------- |
| exactly the planned content | unchanged | never rewrites it                                 |
| absent                      | missing   | writes it, without asking: nothing is overwritten |
| present, different content  | differs   | a conflict: replaced only if a person confirms    |

`.client-site.json` counts as unchanged when it differs only in `generatedAt`
and `cliVersion`. It is ClientKit's own record, never a conflict. It is written
when it is missing, when what it records changes, or when any other file is
written. So a no-op leaves it byte for byte, and any real write updates its
`generatedAt`.

Then:

- **Nothing to write:** "already up to date", exit 0. No question, no post
  step.
- **Only missing files:** written without asking, even with `--yes`.
- **Any conflict:** interactively, the files are listed and the existing
  confirmation is asked, defaulting to no. With `--yes` or without a terminal,
  the run stops and writes **nothing**, not even the missing files. A refusal
  never leaves a half-applied change.

The executor is handed the plan narrowed to exactly the decided paths
(`narrowPlan`). The operations, their order and their content are the plan's
own. There is no second generator.

Post steps follow what was written. A run that writes nothing runs none.
Otherwise install runs only if `package.json` was written, and `git init` only
if there is no `.git` (`postStepsAfter`).

`--dry-run` makes the same decision and shows it: files to create, files to
replace (only with confirmation), a count of unchanged files, or "already up to
date". It lists exactly the paths a confirmed run then writes, `.client-site.json`
included.

## What it cannot tell: edited or just different

ClientKit keeps no record of the bytes it once wrote. A file that differs from
the plan could be:

- your edit;
- a file generated for another configuration, before a stack change;
- a file generated by an earlier ClientKit, whose template has since changed.

These are indistinguishable here, so all three are treated as your work. That
is the conservative choice, and it has a cost. After changing the stack, or
after a ClientKit release that changed a template, files you never edited will
also ask for confirmation. Storing hashes of what was written would lift that,
but it would change every generated project's `.client-site.json`.

## Configuration and template changes

Re-running with a different stack, whether a new component library or a new
framework, is the same decision against a different plan:

- files the new plan needs and that do not exist are added;
- files that differ are conflicts, and need confirmation;
- files the new plan no longer names are left where they are. Nothing proves
  them obsolete, so nothing deletes them. `upgrade` lists them for you.

There is no migration logic per stack. A change the plan cannot express safely
is refused, not attempted.

## Determinism

The decision is a function of the plan and the files it names. Its lists are
sorted by the plan's pinned collator, so it doesn't depend on the order of the
plan's operations, directory listings, the locale or the clock. See
[deterministic-generation.md](./deterministic-generation.md).

## Not included

No line-by-line diff, patches, three-way merge, rollback, backups or deleting
obsolete files. Content is only compared to decide what to write; it is never
merged.
