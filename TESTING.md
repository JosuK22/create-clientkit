# Testing

Most validation in this project is automated and runs in CI — see
[CONTRIBUTING.md](./CONTRIBUTING.md) for the scripts and
[RELEASING.md](./RELEASING.md) for the release gates.

This file records the validation that **cannot** be automated, so that a claim
like "it works on mobile" has a date, a device and a result attached to it
rather than being an impression.

## Real-device mobile validation

### 2026-09-12 — create-clientkit@1.0.1

|              |                                                              |
| ------------ | ------------------------------------------------------------ |
| Package      | `create-clientkit@1.0.1`, installed from the public registry |
| Device       | Motorola Edge 40                                             |
| OS           | Android 14                                                   |
| Browser      | Chrome                                                       |
| Orientations | Portrait and landscape                                       |

Three projects were generated from the published package, installed,
type-checked and production-built, then served with `astro preview` and opened

#### Notes on two checks

**Touch targets.** The Full mode's navigation links measure 39×40, 34×40 and
49×40 CSS px with 16–17px gaps. That is above the WCAG 2.5.8 minimum of 24×24
and below the 44×44 enhanced guideline. Emulation can measure the geometry but
cannot judge whether a thumb finds it awkward; the device pass settled it and
nothing was changed. Worth re-checking if the navigation ever grows.

**Reduced motion.** With `prefers-reduced-motion: reduce`, the heading, main
content and footer all render at full opacity with zero running animations —
no content is hidden behind a transition that never plays.

#### Limitations

This is a record of one device, not a claim about the mobile web in general.

- One device and one browser. Safari on iOS was not tested.
- The tablet row is emulation only — a phone was the available hardware.
- Emulation (72 page/viewport/appearance combinations via Puppeteer) was used
  as a pre-screen for measurable defects — overflow, target geometry, clipped
  text — not as a substitute for the device pass.
- Manual mobile testing is not an accessibility audit. The automated axe gate
  in `npm run smoke:audit` remains the authoritative automated check, and axe
  reporting zero violations is itself not a claim of WCAG compliance.

#### Unrelated finding

Not a mobile defect, recorded here because it surfaced during this pass:
`NAV` entries are rendered by the 404 page but silently ignored by the Coming
Soon home page, which sets `showHeader={false}` because it carries its own
brand lockup. Reproducible by adding `NAV` entries and rebuilding. Left
unchanged — it is identical on desktop and is a template behaviour question,
not a mobile one.
